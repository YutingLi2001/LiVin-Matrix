# Story 1.5.6: GitHub CI/CD环境配置

## Status
Ready

## 你的目标
配置GitHub Actions CI/CD流水线，让代码提交能自动触发测试、构建和部署流程。

## 你需要做的关键操作

### 🔐 GitHub Secrets配置（你必须亲自完成）
- [ ] **导航到Repository设置**
  1. 访问GitHub repository
  2. 进入Settings > Secrets and variables > Actions
  3. 点击"New repository secret"

- [ ] **添加AWS凭据**（如果计划部署到AWS）
  ```
  AWS_ACCESS_KEY_ID=你的AWS访问密钥
  AWS_SECRET_ACCESS_KEY=你的AWS秘密密钥
  AWS_DEFAULT_REGION=us-east-1
  ```

- [ ] **添加GitHub OAuth配置**
  ```
  GITHUB_CLIENT_ID=你的GitHub OAuth Client ID
  GITHUB_CLIENT_SECRET=你的GitHub OAuth Client Secret
  JWT_SECRET_KEY=随机生成的JWT密钥
  ```

- [ ] **添加凭据**（如果使用）
  ```
  DOCKER_USERNAME=你的Docker Hub用户名
  DOCKER_PASSWORD=你的Docker Hub密码
  ```

## 技术背景信息

### CI/CD流水线架构
- **前端流水线**: 测试 → 构建 → 部署到GitHub Pages
- **后端流水线**: 测试 → 构建Docker镜像 → 部署到AWS/云服务
- **触发条件**: Pull Request触发测试，main分支触发部署

### 必需的GitHub Secrets
- GITHUB_CLIENT_ID
- GITHUB_CLIENT_SECRET  
- JWT_SECRET_KEY
- AWS_ACCESS_KEY_ID (可选)
- AWS_SECRET_ACCESS_KEY (可选)
- DOCKER_USERNAME (可选)
- DOCKER_PASSWORD (可选)

### 常见问题排查
如遇到问题，可向dev agent询问：
- 工作流执行失败：检查Actions日志和错误信息
- Secrets配置问题：检查变量名和权限设置
- 部署失败：检查目标环境和网络连接

## Dev Agent Record 🤖

### 配置过程中遇到的技术问题及解决方案

#### 1. GitHub Actions工作流创建 ✅
**问题**: 需要从零开始创建完整的CI/CD工作流配置

**解决方案**: 
- 创建了三个核心工作流文件：
  - `.github/workflows/frontend-ci.yml` - 前端CI/CD流水线
  - `.github/workflows/backend-ci.yml` - 后端CI/CD流水线  
  - `.github/workflows/main-ci.yml` - 主集成流水线
  - `.github/workflows/deploy-frontend.yml` - GitHub Pages部署流水线

#### 2. Node.js版本兼容性问题 ✅
**问题**: Frontend CI失败，Node.js 18版本与项目依赖不兼容
```
Error: Cannot find name 'process'. Do you need to install type definitions for node?
```

**解决方案**:
- 升级GitHub Actions中Node.js版本从18到20
- 安装`@types/node`依赖包
- 更新所有工作流文件使用Node.js 20

#### 3. React Router测试冲突 ✅
**问题**: 前端测试失败，BrowserRouter嵌套错误
```
Error: You cannot render a <Router> inside another <Router>
```

**解决方案**:
- 修复`frontend/src/App.test.tsx`中的路由器嵌套问题
- 移除测试中多余的BrowserRouter包装
- 简化测试用例，专注于基本功能验证

#### 4. 后端服务模块缺失 ✅
**问题**: 后端测试失败，导入错误
```
ModuleNotFoundError: No module named 'app.services.auth_service'
```

**解决方案**:
- 提交之前未跟踪的服务文件：
  - `backend/app/services/auth_service.py`
  - `backend/app/services/email_auth_service.py`
  - `backend/app/services/email_service.py`
  - `backend/app/services/secrets_service.py`

#### 5. PostgreSQL版本语法错误 ✅
**问题**: Backend CI失败，环境变量语法错误
```
Error: env.POSTGRES_VERSION: unbound variable
```

**解决方案**:
- 将`postgres:${{ env.POSTGRES_VERSION }}`硬编码为`postgres:14`
- 简化环境变量配置，避免复杂的变量引用

#### 6. GitHub Pages权限配置 ✅
**问题**: 部署到GitHub Pages失败，权限不足
```
Error: Resource not accessible by integration
```

**解决方案**:
- 简化deploy-frontend.yml工作流文件（从316行减至65行）
- 添加正确的permissions配置：
  ```yaml
  permissions:
    contents: read
    pages: write
    id-token: write
  ```
- 用户需要在Repository Settings > Pages中手动启用GitHub Pages

#### 7. Black代码格式化冲突 ✅
**问题**: Backend CI失败，代码格式不符合Black标准
```
would reformat backend/tests/test_responses.py
```

**解决方案**:
- 直接运行`python3 -m black tests/test_responses.py`让Black应用其首选格式
- 提交Black格式化后的代码，确保与CI/CD检查一致
- 避免手动格式化与Black工具的冲突

#### 8. 系统化问题解决方法 ✅
**关键策略**: 从"打地鼠式"修复转向系统化清理

**实施步骤**:
1. 使用通用代理进行全面代码库清理
2. 批量处理相关问题而非逐个修复
3. 建立一致的代码格式化标准
4. 优先解决影响多个工作流的根本问题

### 学到的经验教训

1. **版本兼容性**: 始终使用最新稳定版本避免依赖冲突
2. **代码格式化**: 让自动化工具处理格式化，避免手动干预
3. **系统化解决**: 批量处理相关问题比逐个修复更高效
4. **权限配置**: GitHub Actions权限设置需要精确匹配功能需求
5. **测试隔离**: 确保测试环境不与实际应用环境产生冲突
